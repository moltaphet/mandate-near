02 / The mandate

Limits before signatures.

Every proposed trade passes the same ordered checks. The first refusal has a named reason. The agent cannot replace the bytes the vault constructs.

01 / Structure

Allowed assets.

Different listed assets, with positive input and minimum output.

02 / Timing

Room between trades.

No outstanding intent, and the configured cooldown has elapsed.

03 / Prices

Fresh enough to decide.

Held and traded assets need accepted, recent oracle data.

04 / Balance

Spend what is held.

The listed Intents balance must cover the proposed input.

05 / Trade size

A cap per request.

Oracle-valued input cannot exceed the owner's trade limit.

06 / Turnover

A daily allowance.

Approved signing requests reserve quota for their UTC approval day.

07 / Slippage

A minimum worth taking.

Minimum output value must fit the allowed oracle-value slippage.

08 / Drawdown

De-risk at the threshold.

When observed NAV trips the drawdown guard, only stable destinations pass.

09 / Position

Keep exposure bounded.

Non-stable position limits apply, with a non-worsening de-risking exception.

The oracle is trusted for market correctness. Stable assets are owner-configured, and freshness does not prove a peg. Pause stops new and unsigned work; an already issued signature remains valid until its deadline.

The practical questions

Know the boundary.

Can the agent withdraw or sign on its own?

The agent can propose trades. It has no owner withdrawal authority or treasury signing authority through the contract API. It can still cause economically harmful trades that fit the mandate. Enforcement also depends on a correctly sealed vault and trusted external contracts.

What does this dashboard actually do?

It reads one final-block snapshot of a public vault: controls, current and queued rules, Intents ledger balances, signing reservations and latest recorded outcomes. It sends no wallet transactions. Unknown history and settlement stay explicitly unverified.

What happens when a withdrawal result is unknown?

A withdrawal may already have been dispatched or debited. Missing or inconsistent proof retains a guard that blocks new withdrawals and trades; elapsed time, a larger balance and owner authority cannot override it. This availability risk is accepted for the current testnet scope. Under the reviewed fresh-issuer and inert-sink prerequisites, voucher proof can establish cancellation or initial debit. Safe retries require owner rearming. Debit proof does not confirm terminal delivery or exclude a later refund. Apply requires 280 TGas; dispatched recovery requires 140 TGas. Live receipt-loss recovery remains unverified.

Does pause cancel a signature that already exists?

No. Pause prevents new execution and unsigned callback work. An already issued intent can remain executable until its stored deadline. The contract reserves signing quota before the signer call.

Is Mandate ready for real funds?

No mainnet readiness is claimed. Governance, oracle availability, a fresh sealed deployment, actual vault MPC and funded settlement, elapsed withdrawals and intended-chain failure recovery remain release requirements.

Does the agent run in a TEE today?

No verified TEE execution is claimed. The agent supports deterministic two-asset rebalancing and optional strict model decisions. OutLayer delivery and attestation are planned; the on-chain mandate remains the authorization boundary.
