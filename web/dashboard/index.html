About

A treasury that checks itself before it signs.

Mandate is a policy layer for NEAR agents. The agent proposes a trade; the vault checks it against nine gates before requesting a contract-derived MPC signature. Owner withdrawals use a separate delayed path.

The agent has no treasury signing key and cannot directly withdraw or change owner controls. A compromised agent can still propose harmful trades that pass the limits and lose money. Deployment authority, the oracle, NEAR Intents and MPC remain trust assumptions.

This sample mode illustrates rules and links their tests. Observed state mode separately reads a selected vault. Public state alone does not establish an actual funded live vault trade.

FAQ

Questions a reviewer would ask.

Each answer says what exists today. Where something is planned, it says so.

Is this trading live on NEAR?

On NEAR testnet only. vault2 signed and settled two trades with a counterparty we control, one of them decided by an admitted model, and both ledgers are recorded. No mainnet trade exists. On testnet the prices are operator-fed and the Intents verifier is a fixture build.

Can the agent move the money?

The agent cannot directly withdraw or sign for the treasury. It can propose trades that the vault approves, so its decisions can change balances and lose money inside the limits. The contract constructs the signed amount, deadline and nonce.

What happens if the price feed fails?

Missing, stale or incoherent data prevents signing. Approved prices must remain within their configured age when signing is requested; equality at the age boundary is allowed. The contract does not re-price or guarantee freshness when an already issued intent settles.

Why this order of locks?

The cheap checks come first: structure, lock and cooldown. Price reads come before the money checks, because the money checks need them. The first closed lock stops the trade, so later locks are not evaluated. The order is fixed, so a rejection always names the same first failure for the same input.

Who can change the rules?

Only the authorized owner. Tightening applies immediately; loosening is queued for 24 hours and can be cancelled. Pause blocks new and unsigned execution work; already issued signatures retain their deadline. These controls are implemented. On testnet the owner is a Sputnik DAO: it set the agent, queued a withdrawal and admitted a model, each through a DAO proposal. A reviewed multisig with independent members is still required for real funds.

What if the agent is compromised or spams proposals?

It can choose harmful permitted trades or disrupt availability. Only one proposal can be pending at a time, and none is accepted while a signed intent is open. Three gate rejections halt proposals until the owner resumes them. Strike counting is implemented and sandbox-tested.

Where is the proof?

Click any lock to see the test that proves its rule and the command to rerun it. The evidence page lists the mainnet checks and the reproduction steps. Nothing on this page needs a key or funds to rerun.

Does the design promise returns?

No. Mandate limits how much can go wrong and who can change the limits. It makes no claim that any strategy is profitable.

Is the data on this page real?

The scenarios and receipt in Sample illustration are fixed data, and its attacks are dated sandbox output. Observed state reads public account views and ledger balances at one final block; it does not re-run trade gates or authenticate settlement receipts.
