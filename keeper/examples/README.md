# Optional relay publication

The keeper's default mode recovers eligible active withdrawals, executes eligible proposals and writes signed intent files to `KEEPER_OUTBOX`. It makes no solver-relay publication requests. An already-issued fresh signature is handed off first. While any withdrawal is active, the keeper waits or calls recovery for that exact attempt; it does not execute a trade, apply a queued withdrawal or rearm an owner-authorized retry.

Explicit publication mode:

```sh
cargo run -p mandate-keeper -- --publish keeper/examples/relay-public.json
```

Set the public config's `metadata_dir` to the agent's public outbox and `expected_chain_id` to the actual reviewed network. The existing keeper account configuration pays only for permissionless `execute` and recovery transactions. The documented partner JWT can be supplied at runtime through `RELAY_AUTH`; never store it in this public file. No operator credentials are needed by the local mock HTTP tests.

The expected chain protects the entire keeper, including `execute`. Public RPC status and final-anchor checks run before signer configuration is loaded, on every tick, and immediately before a transaction. All configured failover endpoints must pass. Default mode can also use the public `EXPECTED_CHAIN_ID` or `NEAR_CHAIN_ID` environment setting; every specified environment/config chain must agree. Omitting all pins still requires a valid public network identity and final anchor, but does not select an expected chain. These public RPC checks detect configuration mismatches; they do not independently authenticate a dishonest RPC server.

Recovery requires the atomic `get_withdrawal_recovery_state` interface and exactly its supported six-field shape: a canonical nonzero U64 attempt ID, a known phase, integer timestamps, a 300-second recovery delay and 140 TGas. Both `unique_voucher_v1` and `durable_withdrawal_journal_v1` accept `Preparing` and `Dispatched`. In journal mode, preparation schedules only authenticated descriptor/admission reads; timeout recovery invalidates that attempt before any payment is sent. Old contracts without this interface, unknown protocols and inconsistent snapshots fail before signing. The keeper reads its decision from one final block, checks the network again, then calls `recover_withdrawal_attempt({"withdrawal_id":"ID"})` with zero deposit and 140 TGas. It obtains no executor address or payment authority from additional RPC fields. A raced newer attempt is unaffected by that old-ID call. A known `false` result has a 30-second cooldown for the same ID; a changed ID is inspected independently. `true` reports recovery resolution, which may only prove a debit or cancellation; this keeper observation does not independently establish final receiver delivery. The voucher protocol cannot resolve permanently missing or inconsistent voucher proof; the journal protocol delegates authenticated status reconciliation to the vault's bound executor.

The binary holds an exclusive `keeper.lock` in the canonical public outbox. It refuses symlink locks, ambiguous directories and another process using that outbox. Do not remove or replace this lock while a keeper is running. Every paid operation is presigned, then its public context and exact transaction hash are written to `keeper-operation.json` and synced before broadcast. The file contains no private key or signed transaction bytes. Only a matched successful transaction with a supported result clears the file. The SDK may retry broadcast of the identical signed transaction; the keeper does not sign a replacement after an ambiguous result.

Transport errors, mismatched or malformed paid results, and receipt failures stop the binary immediately and retain the operation fence. A crash after the fence is written also retains it. On startup any retained operation, including a malformed file, blocks signing before credential loading. This version does not reconcile it automatically: an operator must independently establish the exact transaction and vault outcome before archiving the fence and restarting. Unknown or not-found RPC status is insufficient. Public errors before broadcast use the existing bounded backoff. A normal restart after a known result resets the in-memory cooldown.

Library automation should retain one `KeeperState` and `OperationJournal` and call `tick_guarded`. The compatible `tick` method is a single manual step without durable restart fencing or a cross-tick cooldown; its typed `PaidOutcomeUnknown` error must never be retried automatically.

Before publication, the keeper reads a final block, requires the same current signed result, compares its proposal ID, vault, verifier, exact input/output deltas, signature format and deadlines with the selected quote metadata, then sends the documented `publish_intent` request. A failed or unknown publication is retried with bounded backoff. The same signed nonce remains fixed.

The public `relay-<id>.json` file records acknowledgement only. `relay-observation-<id>.json` records an initial relay status and always keeps `settlement_verified: false`. Status is not continuously monitored by this mode. Independent final transaction/receipt and ledger evidence is still required before describing a trade as settled.
