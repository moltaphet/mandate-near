MANDATE WITHDRAWAL RECOVERY RESEARCH
Date: 2026-11-06
Scope: source inspection, actual-fixture mechanics and local production voucher implementation.
No live deployment, live signing or live receipt-loss/recovery trial was performed.

DECISION
The current local contract implements unique_voucher_v1: one native NEP245 unit
per withdrawal attempt, consumed by either the original atomic withdrawal batch
or a competing cancellation transfer. Targeted mechanics, full lifecycle, minimum
gas and production recovery tests pass as recorded below. Root's complete serial
sandbox run and exact artifact freeze remain separate final verification steps.

Positive sent proof consumes the authorization as DebitObserved; it proves the
initial debit batch, not receiver delivery or absence of a later resolver refund.
Positive cancelled proof permanently blocks delayed originals and requeues only
an unarmed request; owner+1yocto re-arm preserves its original maturity and uses a
NEW id. No timeout, generic balance, nonce-used or operator assertion releases a
Dispatched guard. Preparing timeout invalidates the old id before safe requeue.

Deployment must establish uncreated s.<vault>/c.<vault>, absent Intents signing
or proxy authority, a sealed vault account and no future sink-creation path.
An actual preexisting NEAR sentinel with zero registered Intents keys was shown
to erase proof and permit two debits: this prerequisite is material. Old unknown
pre-voucher operations cannot be retroactively fixed or migrated by this protocol.
Live readiness and universal recovery guarantees remain UNVERIFIED.

1. REPRODUCED INFORMATION GAP

The pre-protocol ActiveWithdrawal records request, id, request_seq, started_sec
and balance_before. Its former balance-only reconciliation accepted a balance at or
below balance_before - requested amount. Consequently:

  baseline 100 -> actual withdrawal debit 20 -> incoming credit 25 -> current 105
  required recovery threshold: current <= 80
  result: guard remains; trading and sending another withdrawal remain blocked.

This observation is indistinguishable from a different history where the old
debit never committed and an unrelated credit of 5 brought the balance to 105.
Blind retry duplicates the old debit in the first history; unconditional release
cannot establish the original action in the second. Extra balance observations
and elapsed time do not add the missing operation identity.

The preserved regression still refuses105 or any scalar balance without genuine
voucher destination proof:

  same_asset_credit_can_mask_an_unknown_debit_and_must_remain_guarded

3. WHY NONCE-USED IS NOT A DIRECT WITHDRAWAL RECEIPT

There is an is_nonce_used(account_id, nonce) view. It records nonce consumption,
not the withdrawal parameters or the terminal external result. Exact upstream
core/src/intents/mod.rs:31-34:

    /// Sequence of intents to execute in given order. Empty list is also
    /// a valid sequence, i.e. it doesn't do anything, but still invalidates
    /// the `nonce` for the signer
    /// WARNING: Promises created by different intents are executed concurrently and does not rely on the order of the intents in this structure

A signed empty nonce-marker payload could be executed independently before a
withdrawal-plus-marker batch. A consumed nonce would then say nothing about the
withdrawal debit. Never interpret a generic consumed nonce as debit evidence.

A unique nonce bound only to one exact signed FtWithdraw payload could prove
initial debit under additional identity/privilege assumptions. That changes the
owner withdrawal path to depend on MPC, and the execute_intents implementation
detaches withdrawal promises rather than returning their U128 result. It still
cannot prove terminal delivery or refund from nonce consumption alone.

V1 nonce history can also be garbage-collected after expiry/salt invalidation.
garbage_collector.rs:41:

            }) => deadline < Timestamp::now() || !self.is_valid_salt(salt),

Non-versioned nonces are currently accepted but versioned.rs explicitly states:

// NOTE: Legacy nonces can still be used at this time, but will be prohibited out in the near future.

A permanent legacy nonce dependency is therefore not recommended for a new
production recovery mechanism.

5. UNIQUE-VOUCHER CANCELLATION RACE

Each attempt gets its OWN token id, amount exactly1, issued exactly once before
sending. This is not a replenishable fungible unit shared by multiple attempts.
The original batch moves it Vault->sent sentinel, then calls ft_withdraw. Recovery
competes by moving the SAME unique unit Vault->cancelled sentinel.

The possible serialized initial-commit outcomes are:
  Original first: voucher is sent; cancellation cannot spend source balance0.
  Cancellation first: voucher is cancelled; every delayed original fails its
  FIRST action, so the same-receipt withdrawal action/debit cannot commit.
  Original's withdrawal action fails: whole initial batch rolls back the voucher
  transfer, leaving cancellation able to consume it.

Both committed destinations must stay inert forever for that id. The issuer
must NEVER re-mint it. Replenishing the same id would let cancellation and a late
original both succeed and would destroy the proof. A retry uses a NEW attempt id.

This provides a source-backed candidate for unknown post-send outcomes without
guessing balances: positive sent proof consumes the old authorization; positive
cancelled proof permits safe requeue. Neither positive proof claims delivery.
No-positive-proof observations and protocol errors keep the guard. Retrying the
cancellation/read can obtain the existing durable destination after its own
callback is lost. Liveness still assumes a progressing, unpaused trusted Intents.
The runtime tests cover both serialization orders. Production recovery chains
also pass against authentic fixture balances, using an explicitly sandbox-only
unknown-guard prestate. Physical receipt-loss/concurrent live scheduling remains
UNVERIFIED; state fixtures and unit callback races are disclosed, not live evidence.

6. PRIVATE ISSUER AND SENTINEL REQUIREMENTS

Implemented native issuer: the vault itself. Actual nep245/deposit.rs authenticates
the token namespace with this exact code:

        let token = env::predecessor_account_id();

Its canonical mapping includes:

            .map(|token_id| Nep245TokenId::new(token.clone(), token_id))

The no-action deposit credits the recipient ledger and returns unused zero:

            return PromiseOrValue::Value(vec![U128(0); token_ids.len()]);

A vault-only issuance step can therefore create a private receipt-shaped asset
nep245:<vault>:<attempt id> directly. Outsiders claiming the vault as sender_id
still receive their OWN predecessor namespace. No general NEP245 storage/token
conformance claim follows; these vouchers are non-financial protocol receipts.
Actual API compatibility and namespace separation are prototype acceptance tests.

Mandatory invariants (local code enforces issuance/id/phase/asset gates; sealed
account and fresh-sink provisioning are external deployment prerequisites):
  - Persist a never-reused id before dispatching its single issuance call.
    No public method lets a caller choose an id, issue amount, recipient or msg.
    No retry or late callback can issue a second unit for that same id.
  - Only the Vault can issue its namespace. Seal account permissions and review
    all registered Intents signing keys/proxy paths. A full-access account key
    would defeat private issuance by calling mt_on_transfer as the vault.
  - Current mandates accept only NEP141 assets. Keep an explicit permanent
    voucher exclusion across every active/queued mandate, trade, withdrawal and
    migration so future asset-type support cannot turn vouchers into assets.
  - Fixed sent/cancelled named uncreated subaccounts under a keyless vault can be
    shared because each token id is unique, e.g. s.<vault> and c.<vault>. They have
    no implicit key and no NEAR account or registered Intents signing key.
    The first prototype proves outside creation/takeover is refused. Setup must
    also establish NEAR account absence, no existing registration/proxy authority
    and no future account creation or Intents registration path. An empty current
    public_keys_of result alone does not establish permanent inertness: a real
    preexisting NEAR account can call mt_transfer directly without an Intents key.
    Supported migration/deployment must require verified fresh/uncreated sinks;
    do not infer that condition merely from names being under the vault.
  - Validate the resulting AccountIds. Prefix/dot requires two extra characters;
    vault names of63/64 characters need another reviewed inert namespace or stay
    unsupported for this recovery setup. Do not silently use a claimable global
    sentinel or assume arbitrary implicit-account non-ownership.
  - Neither vault code nor any issuer/namespace authority can move vouchers back
    out of a destination sentinel. Intents governance/upgrader/privileged roles
    remain an explicit trusted boundary; malicious governance can break proofs.

7. IMPLEMENTED LOCAL STATE/API

Active withdrawal gains explicit Preparing and Dispatched phases. The existing
never-reused withdrawal id can identify the voucher; immutable sentinel derivation
needs no historical list. Callbacks compare both id and phase before any change/send.

Apply: take the authorized pending request, record guard/id/Preparing phase, then
issue exactly1 native voucher through mt_on_transfer under the vault namespace.
Implemented preparation is ONE same-Intents receipt: mt_on_transfer first,
then mt_batch_balance_of(vault,[voucher,victim]) last. Its final callback must
require the exact two-element result [1,sufficient victim balance] for the active
Preparing id before dispatch. This combined preparation's return behavior and full-chain gas passed in the actual production lifecycle
tests below. The local state appends Option<WithdrawalStage> and Option<U64>
request-sequence retry arm, preserving ActiveWithdrawal JSON/Borsh fields.

Send: persist Dispatched phase before building ONE Intents Promise with voucher
mt_transfer first and ft_withdraw last. Each action carries1 yocto. The final
withdrawal Promise keeps the existing identified bounded on_withdrawn handler.

Recover Preparing before any original batch was scheduled: invalidate
that active id/phase before requeue; a late issuance may create an orphan voucher,
but stale callbacks can never build an original withdrawal with it. Never reuse
the abandoned id. This needs a focused late-preparation callback test.

Recover Dispatched: attempt the unique transfer to cancelled sentinel, then query
the sent/cancelled balances. Failed cancellation may mean the original won,
prior cancellation won, or protocol error: failure alone releases nothing.
  sent=1/cancelled=0 -> consume original as DebitObserved, never Delivered/retry;
  sent=0/cancelled=1 -> old original permanently cannot pass its first action;
                     requeue only if original request_seq still current and
                     no replacement/cancelled owner request would be resurrected;
  neither positive -> retain guard and permit another cancellation/query;
  both positive/invalid supply -> fail closed on a broken uniqueness invariant.

Explicit identified U128(0): safe confirmed-refund retry retains the original
authorization but allocates a NEW attempt/voucher id. A late old callback never
modifies a replacement request/operation. Unknown error never blindly retries.

Existing pre-voucher unresolved operations cannot be retroactively protected.
They need an authentic external receipt proof/journal or remain blocked. No
owner assertion or timeout retrofits a voucher into an old committed debit.

8. STORAGE, GAS, BUDGET AND DEPLOYMENT CRITIQUE

Vault storage remains constant-size configuration, counters and one active phase;
status queries inspect at most sent/cancelled/source balances for one fixed id.
Intents stores a distinct total-supply/balance entry per voucher. This external
journal grows over time; each call remains bounded, but its real staking sponsor
and per-operation bytes must be measured and disclosed.

A hard lifetime voucher cap can lock the withdrawal path: any caller can retry a
matured, permanently-refunding request or failed preparation and consume ids.
Implemented guard: a queued owner request arms ONE automatic attempt. Apply
spends that arm before issuance. Safe failure/cancellation may preserve the matured
request, but leaves it unarmed. Only an explicit owner call with1 yocto can re-arm
the same current request without resetting its original 24h maturity. Keep the arm
associated with request_seq so late callbacks cannot re-arm/change a replacement.
Every retry still gets a NEW id; never replenish an old sent/cancelled unit.
Permissionless keepers cannot endlessly mint ids against a permanently-refunding
request. A budget, if additionally introduced, must remain owner recoverable and
stop before dispatch; never silently fall back to an unmarked withdrawal.

The native-voucher design avoids a separate token deployment, supply contract,
FT storage registration and external issuer upgrade authority. It adds issuance,
proof reads, one extra same-receipt marker action and cancellation gas/yocto cost.
The implemented240-TGas entry reserves issuer30 + batch read10 + callback180;
the callback reserves marker30 + withdrawal100 + final callback30. Dispatched
recovery requires110 TGas, reserving cancellation30 + callback70, which then
reserves two reads10+10 + proof callback30. The measured target tests below use
these stated minimums. Exact mainnet staking sponsor, worst-account-length costs
and live provider/permission setup remain UNVERIFIED.

Local review gates completed: fixture mechanics, targeted phase/id regressions,
independent source review, implemented protocol/migration and production-shaped
minimum-gas recovery tests. Remaining release gates: root's complete serial
sandbox/whole-workspace final verification, exact artifact identity and external
permission/sink/oracle readiness. Fresh live receipt evidence requires separately
authorized exact transactions and has not been run.

The cancellation design is not a universally deployed guarantee. Plain
balance/nonce recovery remains insufficient. For existing unknown
operations and any configuration where private unique vouchers cannot be proved,
the exact external blocker is an authenticated durable operation journal or an
on-chain verified receipt/outcome proof.
