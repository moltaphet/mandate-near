## Implemented boundary

The shared commitment/schema crate is consumed by both the vault and a native
overlay on the pinned Intents custody executor. Executor initialization fixes a
ledger domain and 1–20 admitted vaults. Exact requests are permanently bound to
their authenticated vault/attempt ID; debit, Pending and transfer dispatch commit
in the same receipt. The actual resolver records full delivery or atomically
refunds the same ledger. Cancellation of an absent key writes a permanent bound
tombstone. A fresh vault explicitly selects that protocol and reconciles only an
exact authenticated Delivered/Refunded/Cancelled record.

Preparing performs descriptor/admission reads before a guarded dispatch. A lost
vault notification is recoverable after an executor terminal record commits.
A missing executor resolver may leave Pending indefinitely; no finalized-receipt
proof verifier exists. Unknown legacy sends acquire no retrospective facts.
Ordinary reviewed NEP141 semantics and executor ledger/admin/upgrade authority
remain trusted. Storage and gas at supported boundaries require runtime evidence.

The keeper uses ID-bound recovery and a single-writer operation journal that
records the exact public transaction hash before paid broadcast. Ambiguous
outcomes retain a restart fence and require operator reconciliation. An unknown
or not-found transaction cannot authorize a blind retry. Owner rearm and a fresh
payment remain separate authorizations.

Two paid-result edges were corrected during review. The SDK reconstructs a
transaction view without the original reference block hash, substituting the
reported transaction hash; the keeper now compares the full expected SDK
projection while preserving signer, receiver, nonce, key, actions and version.
It does not claim that RPC reveals the original signing anchor. The SDK also
drops `final_execution_status`; the keeper separately requires an explicit
FINAL response for the exact transaction and matching result bytes before
clearing the operation fence. Optimistic, missing, mismatched and Started
results stay ambiguous. Pending results are rejected before outcome access,
avoiding the SDK's pending-outcome panic and retaining the fence. These are
consistency checks against the configured RPC, not authentication of an
untrusted RPC or proof of terminal custody delivery.
