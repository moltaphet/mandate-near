# Spike R1 — can the vault contract be the sole signer on NEAR Intents?

Question (from [ARCHITECTURE.md](../ARCHITECTURE.md) §7): can a NEAR contract
obtain an Ed25519 signature from the MPC network (`v1.signer`) that the NEAR
Intents verifier (`intents.near`) accepts for a swap?

Status: **Historical signature-interoperability evidence (2026-10-31).** A
separate testnet spike contract obtained an MPC signature accepted by mainnet
`simulate_intents` under the derived key's implicit account. This supports
continuing the contract-authorized-signing design; it is not a mainnet-readiness
GO, a named vault's live key registration, or funded vault settlement.

The source/RPC observations and results below retain their original dates.
Current deployed source, external roles and transaction receipts must be
verified independently before real funds.

## Findings from source (commit-level reading, 2026-10-31)

| # | Fact | Source |
|---|---|---|
| F1 | `execute_intents` always verifies a signature from a key registered to `signer_id`. There is no predecessor-auth path for swaps. | `near/intents` `contracts/defuse/core/src/engine/mod.rs::execute_signed_intent` |
| F2 | A contract can register a key for its own account without a signature: `add_public_key` uses predecessor auth (on by default) and needs 1 yocto. | `contracts/defuse/src/contract/accounts/mod.rs` |
| F3 | The `raw_ed25519` standard verifies Ed25519 over the **exact UTF-8 bytes** of the payload JSON string. | `contracts/defuse/core/src/payload/raw.rs` |
| F4 | An implicit account's own key counts as registered. | `contracts/defuse/src/contract/accounts/account/mod.rs::has_public_key` |
| F5 | Legacy random 32-byte nonces are accepted. Versioned V1 nonces add expiry and salt checks. | `engine/mod.rs::verify_intent_nonce` |
| F6 | MPC `sign` takes `{request: {path, payload_v2: {"Eddsa": "<hex>"}, domain_id}}`, requires exactly 1 yocto deposit, and accepts EdDSA payloads of **≤ 1232 bytes**. | `near/mpc` `crates/contract/src/api/sign.rs`, `near-mpc-crypto-types/src/primitives.rs` |
| F7 | When MPC responds, the contract checks the signature with `env::ed25519_verify(sig, message, derived_pk)`. The Intents verifier uses the **same host function**. So any signature MPC returns is valid for `raw_ed25519` by construction. | `near-mpc-signature-verifier/src/lib.rs`, `intents/crates/crypto/src/ed25519.rs` |
| F8 | Response shape: `{"scheme": "Ed25519", "signature": [..64 bytes..]}`. | `near-mpc-crypto-types/src/primitives.rs::SignatureResponse` |
| F9 | `derived_public_key(path, predecessor, domain_id)` is a view method, so the vault's Intents key is known before deployment. | `crates/contract/src/api/keys.rs` |

## Part 1 — golden test against live `intents.near` (PASSED)

`spikes/r1-intents-signing` builds payloads exactly as the vault will. It
signs them with a local Ed25519 key standing in for MPC, then calls
`simulate_intents`, a free view, on mainnet:

| Case | Expected | Result |
|---|---|---|
| Valid signature, empty intents | accepted | PASS (`intents_executed` returned) |
| Payload changed after signing | `invalid signature` | PASS |
| `verifying_contract` = `evil.near` | `wrong verifying_contract` | PASS |
| Valid `token_diff`, unfunded account | fails on balance, **not** signature | PASS (`insufficient balance or overflow`) |

A `token_diff` payload is 382 bytes, well under the 1232-byte MPC limit.

Reproduce:

```bash
cd spikes/r1-intents-signing && cargo run --release
```

## Part 2 — contract → MPC → intents.near (PASSED)

Setup:

- `spikes/r1-mpc-contract` is deployed on testnet as `mandate-r1-4715a0.testnet`.
- It calls `v1.signer-prod.testnet.sign` with
  `{path: "intents", payload_v2: {Eddsa: <hex>}, domain_id: 1}`, attaching
  1 yocto and 30 TGas, and returns the MPC response from a `#[private]`
  callback with 10 TGas.
- It was built with plain `cargo build --target wasm32-unknown-unknown
  --release` on Rust 1.95.0. nearcore accepted the wasm, so cargo-near is not
  required.

Flow (`spikes/r1-part2.sh mandate-r1-4715a0.testnet`):

1. Read `derived_public_key("intents", <contract>, 1)` →
   `ed25519:6dn7BHkg3cTuM5s9nnXc6Vkf14pEHZpvtcDKaR8q3ZeT`.
2. Build the payload with `signer_id` = that key's implicit account (F4).
3. The contract requests the signature. MPC returns
   `{"scheme":"Ed25519","signature":[64 bytes]}` in the same transaction,
   within 100 TGas prepaid.
4. Verify locally with ed25519 `verify_strict`, then submit to **mainnet**
   `intents.near.simulate_intents`.

| Case | Expected | Result |
|---|---|---|
| MPC-signed, empty intents | accepted | PASS (`intents_executed`) |
| MPC-signed `token_diff`, unfunded | fails on balance, not signature | PASS (`insufficient balance or overflow`) |

Testnet MPC was used for signing because NEAR Intents has no testnet. This is
sound because the verifier is network-agnostic about the key. Mainnet
`v1.signer` uses the same contract code and has its own live Ed25519 domain.

### What this historical spike did not prove

- Mainnet `v1.signer` signing for a mainnet contract. Same code, different
  network. It will be exercised in the first real mainnet trade.
- `add_public_key` from the vault on `intents.near` and a real
  `execute_intents` with funds. F2 is confirmed from source only.
- A full execution gas budget with the intended live contracts. Subsequent
  sandbox measurements are recorded separately in `docs/evidence/gas.txt` and
  `docs/evidence/gas-limit.txt`; they use stand-in external components.

## Follow-up: payloads built by the vault's own code (PASSED)

The spike now depends on the contract crate itself, so it signs payloads
produced by `mandate_vault::intent::token_diff_payload` with a V1 nonce from
`mandate_vault::intent::v1_nonce`. That is byte-for-byte the code the vault
will run.

V1 layout, from `near/intents` `contracts/defuse/core/src/nonce/versioned.rs`
(32 bytes):

`5628f6c6 ‖ 00 (V1) ‖ salt (4) ‖ deadline ns (i64 LE) ‖ random (15)`

The salt comes from the live `intents.near.current_salt()` view
(`252812b3` on 2026-10-31). Upstream notes that legacy random nonces
"will be prohibited out in the near future".

| Case | Expected | Result (mainnet `simulate_intents`) |
|---|---|---|
| Vault-built `token_diff`, V1 nonce with live salt, unfunded | fails on balance only | PASS (`insufficient balance or overflow`) |
| Same, salt that `intents.near` never issued | `invalid salt` | PASS (proves the nonce is parsed as V1, not legacy) |

Reproduce: `cd spikes/r1-intents-signing && cargo run --release` (6 cases).

## Design consequences (apply to the vault)

- Use `raw_ed25519`. It needs no extra hashing, and the payload is what MPC signs.
- The payload string is built **on-chain** by the vault, then signed byte for byte.
  Any later change makes it invalid (Part 1, case 2).
- Use V1 expirable nonces in production so nonce storage on `intents.near`
  does not grow without bound. Read the salt from `current_salt`.
- Budget gas: MPC needs ≥ 15 TGas attached, plus our own callback.
