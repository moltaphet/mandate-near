Arithmetic, time, storage and panic conclusions:

- Token amounts use u128 internally and U128 at JSON boundaries. USD arithmetic uses integer valuation with wide intermediates; sell notional rounds up and minimum receipt rounds down. The reviewed 6/24-decimal paths have meaningful tests. No verified valuation overflow exploit was found.
- Release overflow checks are enabled. Some u64 timestamps/IDs use ordinary addition/increment; current runtime dates and realistic sequence counts do not approach overflow. This is not a demonstrated attacker-controlled overflow.
- Cooldown uses saturating_add; daily bucket is now - now % 86,400; turnover uses saturation and a u64-derived cap. Exact allowed boundaries pass. A trade immediately before and immediately after UTC midnight can use each day's allowance; that follows the stated UTC-day policy, not a rolling-window guarantee.
- Time comes from NEAR block timestamp converted from nanoseconds to seconds. Proposal TTL=60, signing window=300, intent TTL=120, maximum execution lock=420 seconds. F07 concerns callback acceptance, not an arithmetic error in 300+120.
- Collections are bounded in count by MAX_ASSETS=20 and single queue slots. They are not all fixed in byte size: the NEP245 suffix problem is F12. No arbitrary new-account or access-key creation is exposed by the vault.
- Static callback budgets do not establish universal sufficiency. Supported-size sandbox execution passed, but oversized/unexpected external answers and a different live external implementation require validation. Gas burnt is different from gas reserved across receipts.
- NEAR receipt-local panic rollback does not undo earlier committed receipts. Execution callback panic/out-of-gas may leave an existing timed lock; registration callback panic can be retried. Withdrawal callback failure lacks an equivalent complete reconciliation path.
- Every on_* callback is #[private]. A negative test demonstrating rejection from a non-self predecessor remains missing; reading the annotation alone is not runtime execution evidence.

B3. WITHDRAWAL AND SR-1 RECOVERY TRACES

Withdrawal:
1. Owner requests a positive NEP141 mandate amount to an AccountId; active execution/open signature refuses it. New request replaces the queue and sets now+86,400. Replacement cannot make a new request mature faster.
2. Owner can cancel the visible request. Anyone can apply at effective_sec exactly or later; execution/signature guards are checked again.
3. The queue is removed before ft_withdraw, preventing duplicate immediate sends of that visible request. No in-flight withdrawal identity/lock is stored: F06.
4. Receipt Err restores the original request only when the visible queue is empty; newer replacement/cancellation history is forgotten: F08.
5. Successful zero return after refunded FT failure is treated as completion: F05. A malformed return or callback failure is not a proven automatic retry/reconciliation path.
6. No direct faster-than-24-hour initial owner drain was verified. F08 permits resurrection with an old matured authorization. F01/F02 concern recoverability, not a new withdrawal-delay arithmetic bypass.
7. token_account() strips exactly one leading nep141: and rejects only an empty remainder. Normal request also requires mandate membership; mandate validation constrains the account characters and length, but does not implement full AccountId grammar. An arbitrary external caller cannot choose a withdrawal asset or receiver.
8. Receiver equal to vault is F02. Receiver equal to intents.near is accepted; exact FT/Intents accounting outcome and recoverability are UNVERIFIED and require an end-to-end fixture test. Do not claim it safely credits the owner's ledger without that test.

Execution/signing:
1. execute takes a monotonically allocated ID and records started_sec before its balance call.
2. Failed balance/price/asset/salt reads invoke failure paths and release the lock without a strike. Gate rejection consumes the proposal and counts a strike. A receipt that never reaches those branches may leave the existing timed lock.
3. on_salt builds no new intent at or after started_sec+300. Deadline is taken from the gate approval state; delayed salt processing does not extend that stored deadline.
4. Signer receipt Err frees the lock. A malformed successful signer result retains it until the timed limit. Whether every real signer failure/timeout mode has the assumed external outcome is UNVERIFIED.
5. At started_sec+420, the lock no longer blocks proposing/executing. Given construction within the 300-second window and 120-second lifetime, no old intent should still be valid then. Full live MPC failure/recovery receipt behaviour remains untested.
6. Identity remains present even after time expiry. A late callback before the next execute changes the ID can still act: F07. A callback after a new execute has installed another ID is rejected; the existing test covers that narrower case.
7. Withdrawal has no corresponding bounded lock/reconciliation record. Merely porting a timeout that blindly resends would risk duplicate withdrawals; recovery must establish whether the previous send transferred or refunded funds.
